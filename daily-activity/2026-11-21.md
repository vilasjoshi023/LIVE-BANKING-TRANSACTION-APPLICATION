# 21 November 2026 – Cassandra JVM, Thread-Pool and Gossip Diagnostics Follow-up

## Objective
Continue the three-node Cassandra performance investigation by reviewing garbage-collection statistics, thread-pool queue state and dropped-message counters. The objective is to determine whether the previously observed higher LAB2 local table write-latency average is accompanied by JVM or Cassandra stage congestion.

## Environment
- Cluster: `VJCLAB`, Apache Cassandra 4.1.12, datacenter `dc1`.
- Nodes: VJC9LAB1 (192.168.62.134), VJC9LAB2 (192.168.62.135), VJC9LAB3 (192.168.62.136).
- Read-only diagnostics executed with `nodetool gcstats` and `nodetool tpstats`.
- No configuration changes or service restarts were performed.

## Activities performed

### 1. Garbage-collection statistics
The latest supplied GC snapshots reported:

| Node | Interval (ms) | Max GC elapsed (ms) | Total GC elapsed (ms) | Collections |
|---|---:|---:|---:|---:|
| LAB1 | 5,444 | 20 | 20 | 1 |
| LAB2 | 2,902 | 36 | 36 | 1 |
| LAB3 | 10,600 | 21 | 21 | 1 |

- An earlier LAB1 capture in the same terminal output reported 16 ms maximum and total GC elapsed.
- LAB2 had the highest maximum pause in this sample (36 ms), but this is a single short observation and does not establish a GC bottleneck.
- These figures are snapshots and should be correlated with sustained workload and time-series GC metrics before tuning.

### 2. Thread-pool statistics
- LAB2 `nodetool tpstats` showed 0 Active, 0 Pending and 0 Blocked tasks across the displayed pools at capture time.
- LAB3 `nodetool tpstats` also showed 0 Active, 0 Pending and 0 Blocked tasks across the displayed pools at capture time.
- The LAB1 `tpstats` output was not present in the captured terminal output. LAB1's GC command returned output, but a complete thread-pool table was not captured; this remains outstanding.
- No thread-pool queue buildup was visible in the supplied LAB2/LAB3 snapshots.

### 3. Dropped-message counters
The supplied `tpstats` dropped-message section showed:

| Message type | LAB2 dropped | LAB3 dropped |
|---|---:|---:|
| `GOSSIP_DIGEST_SYN` | 2 | 12 |
| `GOSSIP_DIGEST_ACK` | 2 | 139 |
| `GOSSIP_DIGEST_ACK2` | 0 | 0 |
| `ECHO_REQ` | 0 | 1 |

- Other displayed entries, including `MUTATION_REQ`, `MUTATION_RSP`, `READ_REQ` and `READ_RSP`, showed zero dropped messages in these snapshots.
- Dropped-message counters are cumulative counters, not necessarily events from the current test interval. They must be compared as deltas across a known observation period and interpreted with each node's uptime.
- LAB3's higher cumulative Gossip drop counts warrant a follow-up check, but do not alone prove a current Gossip or cluster-health incident.

## Results and validation
- Latest reported maximum GC pauses were short: LAB1 20 ms, LAB2 36 ms and LAB3 21 ms.
- LAB2 and LAB3 showed no active, pending or blocked thread-pool tasks at capture time.
- The current snapshots do not demonstrate sustained GC pressure or thread-pool congestion as the cause of LAB2's earlier higher local average write latency.
- LAB1 thread-pool output and node uptime context are still missing.
- No database configuration change, restart, repair, compaction or workload increase was performed.
