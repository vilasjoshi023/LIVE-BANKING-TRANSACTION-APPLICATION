# 25 November 2026 – Continuous Cassandra Slow-Query Monitoring Setup

## Objective
Build a repeatable 100-query synthetic read workload for the banking application, capture per-query latency, publish latest-run performance metrics to Prometheus through the Node Exporter textfile collector, and prepare a systemd timer and Grafana dashboard panels for continuous monitoring.

## Environment
- Cluster: `VJCLAB`, Apache Cassandra 4.1.12, datacenter `dc1`.
- Nodes: VJC9LAB1 (192.168.62.134), VJC9LAB2 (192.168.62.135), VJC9LAB3 (192.168.62.136).
- Workload host: VJC9LAB1, application root `/opt/banking-app`, Python virtual environment `/opt/banking-app/venv`.
- Keyspace/table: `banking_stream.bank_transactions`.
- Monitoring: Node Exporter on LAB1 at `192.168.62.134:9100`; Prometheus at `192.168.62.134:9090`; existing Grafana dashboard `Banking Application - DBA Monitoring`.
- All test data and query traffic described here are synthetic lab activity, not customer or production banking traffic.

## Activities performed

### 1. Pre-test cluster baseline
- `nodetool status` showed all three nodes in `UN` state.
- `nodetool compactionstats` reported `pending tasks: 0`.
- A CQL partition lookup against `banking_stream.bank_transactions` for `transaction_date='2026-11-18'` returned ten sample rows.
- The note from `nodetool status` about differing replication settings in non-system keyspaces was not treated as a node failure.
- An initial attempt to pass a multiline query to `cqlsh -e` failed because the shell invocation did not supply the query as one argument. The same read-only query succeeded in interactive cqlsh; no database change was needed.

### 2. Slow-query workload design and integration
- Created `src/slow_query_lab.py` to execute exactly 100 sequential read requests per run: 50 partition-key lookups and 50 account-filter lookups.
- Query A filters by the partition key `transaction_date`.
- Query B filters by `transaction_date` and `account_id`, where `account_id` is not part of the table primary key. It uses `ALLOW FILTERING` with a single date partition and `LIMIT 10` as a bounded lab anti-pattern demonstration. This is not a recommended production access pattern.
- The first execution attempt failed at Python import time because the test script attempted to import global `session` and `cluster` names that are not exported by `src.cassandra_connection`.
- Inspected the existing application modules and confirmed the supported connection pattern is `cluster, session = get_cassandra_session()`. Updated the workload script to reuse this existing connection factory; `src/cassandra_connection.py` was not changed.
- Corrected Query B clause ordering to put `LIMIT 10` before `ALLOW FILTERING`.
- Python compilation of `src/slow_query_lab.py` passed after the integration correction.

### 3. Prometheus metrics exporter
- Created `src/slow_query_metrics_exporter.py`.
- The exporter writes latest-run metrics atomically to `/var/lib/node_exporter/textfile_collector/banking_slow_query.prom`.
- Metrics are split by a bounded `query_type` label with values `A_PARTITION_LOOKUP` and `B_ACCOUNT_FILTER`; account IDs and transaction details are not exposed as Prometheus labels.
- Exported metrics include latest-run request, success, error, slow-request, rows-returned counts; average, P50, P95, P99 and maximum latency in milliseconds; and the latest-run Unix timestamp.
- The lab slow-request threshold is 100 ms. It is an initial exercise threshold, not a production SLA.
- Updated the workload script to create timestamped CSV files under `/opt/banking-app/logs/` and invoke the exporter after each completed run.
- Python compilation passed for both `src/slow_query_lab.py` and `src/slow_query_metrics_exporter.py`.

### 4. Manual workload and monitoring validation
- Ran one manual 100-query batch on 25 November 2026 at approximately 13:00. All 100 queries succeeded with zero failures.
- The run generated `logs/slow_query_lab_20261125_130039.csv` and the Prometheus textfile metrics.
- First completed monitoring run results:

| Metric | A: partition lookup | B: account filtering |
|---|---:|---:|
| Queries | 50 | 50 |
| Average latency | 11.563 ms | 17.300 ms |
| P50 | 9.076 ms | 15.356 ms |
| P95 | 20.286 ms | 30.672 ms |
| P99 | 36.884 ms | 34.764 ms |
| Maximum | 36.884 ms | 34.764 ms |
| Failed queries | 0 | 0 |
| Slow queries at 100 ms threshold | 0 | 0 |

- Query B average latency was approximately 1.50 times Query A in this run. This is a single-run observation and a candidate for further investigation, not proof that `ALLOW FILTERING` is the only cause.
- A subsequent manual systemd service test at approximately 13:09 also completed 100/100 successfully. It reported:

| Metric | A: partition lookup | B: account filtering |
|---|---:|---:|
| Average latency | 20.167 ms | 31.196 ms |
| P50 | 15.577 ms | 26.256 ms |
| P95 | 36.784 ms | 58.504 ms |
| P99 | 61.388 ms | 77.598 ms |
| Maximum | 61.388 ms | 77.598 ms |
| Failed queries | 0 | 0 |

- Results differed between runs, reinforcing the need for time-series monitoring and repeated comparable samples. The benchmark is synthetic, sequential and limited to a small lab partition; it must not be interpreted as production capacity or an SLA.

### 5. Node Exporter and Prometheus verification
- Verified Node Exporter systemd configuration. The active drop-in `/etc/systemd/system/node_exporter.service.d/textfile.conf` includes `--collector.textfile.directory=/var/lib/node_exporter/textfile_collector`.
- The metrics file was `root:root` mode `0644`, and the `node_exporter` account could read it.
- The initial query to `127.0.0.1:9100` returned no matching output because the Node Exporter service was bound to `192.168.62.134:9100`. Querying the configured address exposed the metrics.
- The endpoint returned both query-type series for the exported metrics, and `node_textfile_scrape_error 0` confirmed no textfile collector scrape error.
- Queried Prometheus at `http://192.168.62.134:9090/api/v1/query` for `banking_slow_query_last_run_latency_ms_p95`. Prometheus returned a successful vector response with two series:
  - `A_PARTITION_LOOKUP`: 20.286 ms
  - `B_ACCOUNT_FILTER`: 30.672 ms

### 6. systemd service and timer preparation
- Created `/etc/systemd/system/banking-slow-query.service` as a root-owned oneshot service with working directory `/opt/banking-app`, Python executable `/opt/banking-app/venv/bin/python`, module `src.slow_query_lab`, and a 120-second timeout.
- Created `/etc/systemd/system/banking-slow-query.timer` with `OnBootSec=2min` and `OnUnitInactiveSec=5min`.
- Ran `systemctl daemon-reload` and `systemd-analyze verify` on both unit files; no verification errors were printed.
- Manually started `banking-slow-query.service`. The journal showed all 100 requests succeeded, CSV and Prometheus metrics were written, the Cassandra connection was closed, and the oneshot unit deactivated successfully.
- **The timer has not yet been enabled.** No recurring automatic workload has been confirmed as running.

## Issues and resolution
- Python import error: attempted to import non-existent module globals `session` and `cluster`. Resolved by using the established `get_cassandra_session()` factory.
- CQL clause ordering: adjusted Query B so `LIMIT 10` precedes `ALLOW FILTERING`.
- Missing exporter initially: created the exporter module and integrated it into the workload script.
- Node Exporter metric query initially returned no output on loopback. Identified the configured bind address as `192.168.62.134` and queried the correct address.
- Textfile scrape: resolved/validated through configured collector directory, readable metrics file and `node_textfile_scrape_error 0`.
