# 18 November 2026 – Cassandra Workload Benchmarking and Performance Diagnostics

## Objective
Run controlled synthetic banking-transaction workloads and review Cassandra node, JVM, thread-pool, memory and disk indicators. Investigate an earlier higher local table write-latency average reported on LAB2 without changing live Cassandra configuration.

## Environment
- Cluster: `VJCLAB`, Cassandra 4.1.12, datacenter `dc1`.
- Nodes: VJC9LAB1 (192.168.62.134), VJC9LAB2 (192.168.62.135), VJC9LAB3 (192.168.62.136).
- Keyspace/table: `banking_stream.bank_transactions`; NetworkTopologyStrategy, RF=3 in `dc1`.
- Workload application: Python Cassandra driver 3.29.3; session write consistency `LOCAL_QUORUM`.
- Tests were synthetic lab workloads, not real banking or customer transactions.

## Activities performed

### 1. Synthetic transaction workload tests
- Ran a 100-record sequential baseline: 100 successful writes, 0 failures; 69.81 TPS; application P50 8.882 ms, P95 41.351 ms and P99 114.189 ms.
- Ran 1,000 sequential writes: 1,000 successful, 0 failures; workload time 10.864 seconds; 92.05 TPS; P50 7.031 ms, P95 31.693 ms and P99 56.069 ms.
- Ran a 500-record concurrent test with 4 workers: 500 successful, 0 failures; 103.20 TPS; P50 26.211 ms, P95 113.534 ms and P99 152.230 ms.
- Ran the corrected 1,000-record concurrent test with 4 workers: 1,000 successful, 0 failures; workload time 5.426 seconds; 184.31 TPS; successful-write P50 16.678 ms, P95 46.820 ms and P99 87.165 ms.
- The date partition count for 2026-11-18 reached 2,600 after these tests. The per-node table write counters increased by 1,000 on each node during the final 1,000-write test, consistent with RF=3 replication.
- Sequential versus concurrent results are single-run lab observations, not a controlled benchmark, production capacity estimate or SLA. Concurrent execution improved observed throughput in this run but increased request latency percentiles.

### 2. Cluster and Cassandra checks
- Latest recorded `nodetool status` and `nodetool describecluster` checks showed all three nodes UN, with one common schema version and no down, unreachable, joining, leaving or moving nodes.
- Pending compactions were 0 after the workload. The inspected LAB1 thread-pool snapshot from the earlier check also showed no active, pending or blocked tasks.
- `nodetool tablehistograms banking_stream bank_transactions` returned 0.00 microseconds for the displayed read/write latency percentiles on all three nodes. These values were not useful for latency comparison and were not treated as proof of zero latency.
- `nodetool proxyhistograms` returned an `InstanceNotFoundException` for the `ClientRequest/RangeSlice/Latency` JMX metric on LAB2. LAB3 displayed zero percentile values. This is a diagnostic limitation to investigate, not evidence by itself of a node outage.
- Earlier manually collected table statistics showed local average write latency of approximately 0.251 ms on LAB1, 1.765 ms on LAB2 and 0.227 ms on LAB3. Corresponding average read latencies were approximately 3.841 ms, 9.593 ms and 6.980 ms. These are cumulative node-local averages with different counter histories; LAB2 had been restarted, so the difference is a lead for further investigation, not a confirmed incident.

### 3. Host resource and disk-I/O checks
- `vmstat 1 5` on all three nodes showed zero swap-in/swap-out and 0% I/O wait in the sampled intervals. No blocked processes were observed.
- LAB1 showed about 282 MB free memory in the sample; LAB2 about 193 MB; LAB3 about 190 MB. Linux cache was also present, so the `free` column alone was not treated as a memory-pressure indicator.
- Fresh `iostat -xz -y 1 5` samples showed very low disk activity. LAB2 had sparse writes, with a maximum observed interval write wait around 6.75 ms, queue depth up to 0.04 and device utilization up to 0.80%. LAB3 showed sparse writes, around 0.75 ms maximum observed write wait and up to 0.10% utilization. LAB1 had almost no disk activity in its interval samples.
- These short, low-I/O samples do not indicate sustained disk saturation and do not explain the earlier LAB2 average-latency difference.

### 4. JVM GC and thread-pool checks
- Latest reported GC maximum elapsed times: LAB1 20 ms, LAB2 36 ms and LAB3 21 ms. Each latest sample showed one collection. LAB2 was slightly higher, but these short samples do not establish a GC bottleneck.
- LAB2 and LAB3 `nodetool tpstats` outputs showed 0 active, 0 pending and 0 blocked tasks across the displayed pools at capture time.
- The LAB1 `tpstats` output was not successfully captured in the supplied terminal log and remains outstanding.
- Dropped-message counters were cumulative: LAB2 reported 2 `GOSSIP_DIGEST_SYN` and 2 `GOSSIP_DIGEST_ACK`; LAB3 reported 12 `GOSSIP_DIGEST_SYN`, 139 `GOSSIP_DIGEST_ACK` and 1 `ECHO_REQ`. These counters need uptime context and before/after deltas; they are not proof of a current gossip incident. Mutation and read-response dropped counters in the displayed results were 0.

## Results and validation
- All transaction writes in the recorded 100, 1,000 sequential, 500 concurrent and 1,000 concurrent runs succeeded.
- The 2,600-row date-partition count and per-node write-counter increments were consistent with the completed workload and RF=3.
- No current disk saturation, active swapping, material I/O wait, sustained thread-pool queueing or major GC pause was demonstrated by the supplied samples.
- LAB2's previously higher local average write latency remains unexplained. The histogram output was non-informative, and the proxy histogram command had a missing JMX metric on LAB2.
- Findings are limited by short sampling windows, cumulative counters, a missing LAB1 `tpstats` capture and the absence of a controlled repeated benchmark.

## Issues and resolution
- Issue: `nodetool proxyhistograms` on LAB2 could not find the RangeSlice latency MBean.
- Root cause: Not established. No JMX configuration change was made.
- Action: Record as a diagnostic gap; correlate with Cassandra version/metrics exposure and workload before considering any remediation.
- Issue: `tablehistograms` returned zero latency percentiles.
- Resolution: Treat those percentile values as non-informative for this run; do not interpret them as actual zero request latency.
