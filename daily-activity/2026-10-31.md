## Work and results captured by this date

### Cassandra data model and synthetic data
- Established the three-node Cassandra topology and CQL access using the VJC9LAB1 private IP.
- Created keyspace `banking_stream` using NetworkTopologyStrategy with RF=3 for dc1.
- Created `banking_stream.bank_transactions` with `transaction_date` as partition key and `transaction_id` as clustering column, plus synthetic account, amount, currency, type, status, description and timestamp fields.
- The retained guide recorded 12,100 synthetic transaction rows for transaction date `2026-10-30`. This is the data partition date; it is not asserted to be the date on which every row was generated or loaded.

- Recorded Python 3.9.25 and dependencies: cassandra-driver 3.29.3, Faker 37.12.0, python-dotenv and colorama.
- Connection module used the three Cassandra contact points and DCAwareRoundRobinPolicy with local DC dc1.
- Transaction generator used synthetic UUIDs, account identifiers ACC10000–ACC10099, transaction types DEPOSIT/WITHDRAWAL/TRANSFER, statuses SUCCESS/FAILED/PENDING, INR amounts, Faker descriptions and timestamps.

### Initial workload performance observation
A 1,000-row test was recorded at 6.063 seconds, approximately 164.94 inserts/second.

The 6.063 ms figure was elapsed test time divided by rows. It included generation/setup/shutdown overhead and was not a per-request latency percentile. The notes specifically identified improvements needed: separate attempted/successful/failed counts, per-operation latency percentiles, explicit consistency level, safe error handling/retries and idempotency.

### Monitoring foundation
- Node Exporter 1.12.1 was installed on all three nodes, exposing host CPU, memory, filesystem and network metrics on port 9100.
- JMX Exporter 1.7.0 was attached to the Cassandra JVM as a Java agent on port 9404; port 7199 remained local-only and 9404 was restricted to the Prometheus server.
- Prometheus 3.15.1 ran on LAB1 with seven scrape targets: itself, three Node Exporters and three JMX Exporters. The recorded configuration used seven-day retention and a JMX scrape interval of 30 seconds with a 20-second timeout.
- The JMX metrics response was approximately 1.2 MB and took several seconds to return. This is a monitoring payload/scrape-cost observation, not proof of a database latency incident.
- Prometheus configuration was validated/reloaded; the last recorded target status before shutdown was 7/7 UP.
- Grafana 10.2.6 used Prometheus at `http://192.168.62.134:9090`.

## Errors, RCA and resolutions documented in this snapshot

### CQL localhost connection issue
- **Symptom:** `cqlsh` to 127.0.0.1 failed while connecting to the node's private IP worked.
- **Investigation guidance in the notes:** Use the verified private IP and inspect Cassandra `rpc_address` and native transport if further diagnosis is needed.
- **Root cause:** The exact `rpc_address` value and full error output were not retained, so a precise bind-address root cause is not asserted.
- **Workaround/validation:** Use `cqlsh 192.168.62.134 9042`; connectivity to the private IP was recorded as working.

### Grafana to Prometheus connection denied by SELinux
- **Symptom:** Grafana datasource connectivity/Explore query was denied.
- **Root cause recorded:** SELinux blocked Grafana's outbound TCP connection to the configured Prometheus port.
- **Correction:** Enabled `grafana_can_tcp_connect_prometheus_port` permanently; SELinux was not disabled.
- **Validation:** Grafana Explore successfully queried Prometheus.

### Shutdown script remote verification error
- **Symptom:** The stop script's nested remote-shell verification loop returned an error.
- **Root cause recorded:** Nested SSH/shell quoting was incorrect.
- **Correction/workaround:** Cassandra drain and stop operations were carried out manually on all three nodes; Prometheus, Grafana and Node Exporter were also stopped. The original script still required hardening.

### Cassandra systemd exit status 143 after drain/stop
- **Symptom:** systemd reported Cassandra as failed after the stop sequence; node 2 showed a successful drain followed by main-process exit status 143.
- **Interpretation:** 143 is consistent with SIGTERM (128+15). The systemd state alone was not considered proof that Cassandra remained running.
- **Operational resolution:** Check CassandraDaemon processes and port 9042 on all nodes before powering off; do not blindly clear the failed state or assume process termination from the status label alone.
