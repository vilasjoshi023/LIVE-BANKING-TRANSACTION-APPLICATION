# 16 November 2026 – Failure Recovery, Repair, Backup and Restore

## Objective
Exercise cluster availability during a node outage, validate repair, and practice snapshot-based SSTable restore in a separate target table.

## Environment
Three CentOS Stream 9 VMs running a Cassandra 4.1.12 cluster, one datacenter dc1, replication factor 3 for keyspace `banking_stream`.

## Activities performed

### Controlled node outage and transaction workload
- LAB2 was stopped for a controlled failure exercise; LAB1 and LAB3 remained available.
- Python application used LOCAL_QUORUM to insert 1,000 banking transaction records while LAB2 was down.
- Observed result: 1,000 successful inserts, 0 failures. The run reported 7.393 seconds workload time, 135.27 TPS, average latency 7.062 ms, P50 5.985 ms, P95 12.318 ms and P99 21.048 ms.
- LAB2 was restarted and all three nodes later returned to UN.
- These are results from one lab run, not a production performance benchmark or SLA.

### Repair validation
- Ran a repair preview for `banking_stream.bank_transactions`; preview reported data in sync for the previewed scope.
- Ran incremental sequential repair for the specified keyspace/table on LAB1. The parent repair command and session reported successful completion.
- After repair, the recorded pending compaction count was 0 and all nodes were UN.
- The result applies to the requested repair scope; it does not establish that every keyspace/table has been repaired.

### Snapshot and backup staging
- Created snapshots for `banking_stream` on each node using the tag `banking_backup_20261116`.
- Copied snapshot data into LAB2 staging folders for node1, node2 and node3.
- SHA-256 comparisons passed for all 10 files in node1 and node2 copies. Node3 copy size was checked; a checksum comparison was not confirmed.
- Staging on another VM sharing the same VMware host is not an independent physical disaster-recovery copy.

### Restore exercise
- Created a separate restore target table with matching table schema and primary key.
- Staged SSTable components and used SSTableLoader to stream them into the cluster.
- Loader reached 100%; 7 files and 3.698 MiB were reported.
- For transaction date `2026-11-15`, source and restored counts both returned 3,000. Five sample rows matched across selected fields.
- Original source table and existing `banking_restore_lab.transactions` table were left untouched.

### Snapshot automation
- Created `/usr/local/bin/cassandra_backup.sh` to create timestamped snapshots sequentially on all three nodes and verify snapshot metadata.
- Syntax check passed. First automated run succeeded for all three nodes, taking 55 seconds.
- SHA-256 manifests were generated separately for each node's snapshot files; 30/30 local file comparisons passed.
- Script currently performs snapshots and metadata verification only; it does not yet implement off-host copy, checksum verification, retention or full restore orchestration.

## Results and limitations
- Controlled node outage insert test succeeded for 1,000 transactions.
- Repair preview and the specified incremental repair completed successfully.
- Restore validated the target partition count and selected sample fields, not every partition and every business attribute.
- No retention cleanup was executed. Incremental backup checks on other nodes and enabling incremental backups were deferred.
- RTO/RPO examples discussed are illustrative and have not been measured through a full DR exercise.
